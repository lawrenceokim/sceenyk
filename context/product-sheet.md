## Provider and API contract

`lib/product-sheet/provider.ts` defines `ProductSheetProvider`; the factory returns `OpenAIProductSheetProvider`. Central server-only configuration requires `OPENAI_PRODUCT_SHEET_MODEL=gpt-image-2.5-sunburst`, the existing `OPENAI_API_KEY`, and explicit `UGC_PRODUCT_SHEET_ENABLED=1`. No fallback, new credential, browser API call or public environment variable. Default example enablement is 0. Local startup validates Product configuration before an explicit Product resume; Character-only setup remains valid while Product is disabled. Imports/construction never make requests.

The current [OpenAI Image Edit API](https://developers.openai.com/api/reference/resources/images/methods/edit) and installed official SDK support this exact model. The adapter uses `client.images.edit` (`POST /v1/images/edits`) with a multipart PNG derived from the original owned source on **every** request, `n=1`, `1024x1024`, high quality, opaque background and PNG output. It requests neither a URL response nor Files API uploads. `input_fidelity` is omitted: the fetched reference does not establish that option for Sunburst. Image fidelity must be manually accepted, never inferred from successful API validation.

GPT Image returns base64 image data. The adapter accepts exactly one bounded, strictly encoded image, decodes bytes locally and never routes them through the Higgsfield CDN allowlist/downloader. SDK automatic retries are disabled, timeout is ten minutes, and cancellation uses the worker signal. `X-Client-Request-Id` is the persisted operation UUID for correlation only, **not a claimed provider idempotency guarantee**. Returned request ID and supported numeric token/latency usage are projected into private checkpoints; raw provider bodies, base64, revised prompts, headers and errors are not persisted/logged. Usage fields absent from the response stay null.

## Identity, prompts and provenance

The immutable v3 snapshot supplies the Product / Prop name and exact source asset/fingerprint, settings and project relationship. Completed Product analysis v1 with the same frozen model/source/version is required, as is the completed Character Sheet with matching snapshot/source/name. M6 never reruns validation, either analysis or Character generation. A v2 nameless job is not silently upgraded.

Versioned instructions are frozen in the private Product document once. Three independent edits produce primary/hero, approximately three-quarter angle and detail. Every edit receives the same original private image, conditionally read by ETag through the existing owner/project/role/upload/fingerprint loader, safely decoded/oriented and fitted inside 2048px without cropping. Generated views are never the sole source for subsequent edits. Original visible evidence outranks text analysis. Prompts preserve category, silhouette, proportions, colors, materials, controls, branding and construction; labels/settings/analysis are untrusted data. Project style must not redesign the object. Detail selection uses observed design/features/parts/material/branding; unclear details stay unclear rather than invented.

`provenance` records original-image factual authority, subordinate saved observations and the generated status of **every** output. The angle can require inferred hidden geometry; primary/closeups are generated interpretations too. No new surface, logo, control, port or material is claimed observed merely because a model generated it. This is semantic provenance, not a pixel-level factual mask. Manual inspection determines actual visual consistency.

Binaries stay in private R2, under immutable canonical `ugc/{owner}/{project}/{job}/product-v1/{sheet}/{assetType}.png` keys. Each descriptor has a stable asset UUID, ETag, size, dimensions, SHA256, MIME and centralized asset type. Conditional create-only PUT plus conditional reread validates the persisted bytes. PostgreSQL stores metadata only. No private key, provider ID/document or image enters normal progress DTOs or Templates. Template adopters supply their own image/name; no creator source, analysis, generated view or sheet is reused publicly.

Validation distinguishes per-view generation/missing output, empty/oversized bytes, unsupported format/animation, Sharp decode/dimensions, storage, integrity/checkpoint and composition failures. Accepted media is still PNG/JPEG/WebP, single-frame, at least 256px on each edge, bounded by 20MB/20M input pixels; normalized PNG fits within 2048px. Existing stored objects require full pixel decode, descriptor/hash validation and canonical identity. Safe diagnostics retain only fixed codes, actual available HTTP/request ID, byte count and decode result. No CDN host validation applies to base64 edits. Output validation proves usable media, not product identity correctness.

After all views are privately saved, Sharp contains three 768px square panels on a 2400×832 neutral `#b8b8b8` canvas, with 32px outer margins and 16px panel spacing. ## Checkpoints, expensive-work safety and retries

Every view commits an `intent` with a fresh UUID **before** dispatch. A successful synchronous edit checkpoints `received`, request ID and usage before normalization/storage, then commits `completed` and the saved asset descriptor. Only definite HTTP rejection allows another explicit bounded submission; transport loss, timeout, 5xx or a received output lost before R2 are ambiguous and never automatically replayed. Request IDs are diagnostic receipts, not asynchronous polling/result handles: the Images Edit contract used here is synchronous and supplies no retrievable background job. There is no fabricated submit/poll API.

Before **any** provider request, the service checks canonical R2 assets. A crash after PUT but before SQL can recover that view from validated private bytes using the existing operation. Committed descriptor/hash mismatch or disappearance stops safely. If an intent/received operation lacks recoverable bytes, return `RECONCILIATION_REQUIRED`; an operator must resolve the outcome. Never replace it with a new paid request automatically. A successful primary survives angle/detail failure. Retry only the missing safely rejected view. If three views exist, retry composition/storage only. Checkpoint/lease failure prevents dispatch. All writes require a fresh job claim token, expected stage, unexpired lease and no cancellation.

`product_attempt_count` is a separate bounded three-claim budget. It starts at zero for Product, preserves the existing job's immutable global max/attempt history (including a Character-complete job already at 3/3), and is never reset by resume/retry. Expired Product claims can reclaim to inspect R2/checkpoints; the service cannot replay unresolved intents. Definite rejects/config/source/storage/composition failures use existing explicit retry infrastructure within that Product budget. Cancellation/heartbeat/release still use the existing portable runner and local execution policy. Other stages preserve their existing claim/recovery rules. No unlimited retry or generic uncertain-output bypass is added.

Character completion still makes its existing intentional Product pause. Explicit `--resume-product` checks the same owned immutable job, both analyses and completed Character Sheet before clearing that pause. It creates no replacement job, rewrites no snapshot, resets no attempts and never redoes Character work. Product completion atomically marks the sheet complete, appends `product_reference.complete`, queues `location_reference` with `LOCATION_REFERENCE_NOT_IMPLEMENTED`, releases the claim and stops. Location cannot be claimed, advanced or executed; no handler/resume exists for it.
