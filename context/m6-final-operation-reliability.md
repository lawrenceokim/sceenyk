## Causes verified in source

- The action handler committed merge admission or final approval, then awaited another full `ugc_v3_runtime_read` and complete Studio DTO before returning HTTP success. A timeout in that post-commit refresh therefore returned 503 for an already successful action. A timeout during the mutation itself also leaves its outcome uncertain; it is not evidence of rollback.
- The client treated all unsuccessful POST responses as action failures, cleared its local loading flag, and only polled when the old workspace already contained active work. A lost merge acknowledgement could leave the old workspace showing Ready to merge with no polling; an approval awaiting review also had no polling trigger.
- Workspace hydration repeated project/reference reads and setup/location checks for the workspace and every planned clip. Each action also fetched the Clerk profile and upserted the existing app account before ownership checks. These extra dependencies amplified variable database and Clerk latency.

## Behavior and safety

- The new M6 client opts into a small committed receipt. Merge admission, joined approval, rejection and deletion recovery return it immediately after their existing protected SQL write. Full workspace hydration runs separately. Other clients/actions retain the full-workspace response contract.
- Approval still verifies immutable private output bytes, ETag, size and hash before its unchanged SQL approval/currentness checks. Completion and Preview are rendered from the full current workspace; a browser marker or status response cannot approve or complete anything.
- `GET /api/ugc/v3?scope=final&project=...&package=...&manifest=...` authenticates the request, resolves the existing app account, checks V3 access and the active owned Pro project plus V3 enrollment, then reads only matching join/result/deletion metadata. It returns no storage keys, signed URLs, task input or artifact documents. It creates no account or job. No new SQL function, grant, table or migration is needed.
- Existing accounts' opted-in final actions use authenticated session identity and a database account lookup without fetching/synchronizing the Clerk profile again. Missing accounts use the existing verified synchronization path on actions only. Other generation, account and media flows keep their existing synchronization behavior; no identity or owner cache/fallback is introduced.
- Full workspace inspection shares its common read-only setup/location prerequisites within one request, and reads project/reference inputs in parallel. Per-clip preflight and spending approval remain separate, with unchanged validation and authority checks. No shared cross-user/project cache is introduced.
- A project/package/manifest-bound browser intent persists before the POST and restores status checking after refresh or reopening. It is advisory, expires after 24 hours, and is discarded when lineage changes. Storage events synchronize other same-origin tabs. Browser storage is optional; saved server tasks remain recoverable and SQL still deduplicates concurrent requests.
- Temporary POST/network failures reconcile saved state without another POST. Sequential metadata polling continues during merging, approval uncertainty and deletion. A terminal status triggers a full refresh; a temporary refresh failure retains loading and retries reads. A previously failed merge is not mistaken for the result of an unacknowledged retry.
- Known temporary read failures use bounded backoff. Permanent credentials/schema/permissions/configuration failures remain visible immediately. Repeated connection failures pause with **Check status**. An unconfirmed request with healthy reads after three minutes gives an explicit check/retry message; no mutation is automatically repeated. Existing SQL deduplication and approval idempotence still protect an explicit retry.
- Final Video uses existing purple controls, semantic surfaces, wrapping layouts, small reduced-motion-safe spinners and polite status text: starting/checking a merge, merging, approving/checking approval, deleting and refreshing final status. Conflicting clip/final/package actions are blocked while the operation is unresolved. Preview remains available for the saved video. Technical stage/error codes remain in Progress/Details. A rejection dialog closes when the saved result leaves review, including after a recovered acknowledgement.

Database request budgets are unchanged: the full read remains 30 seconds and mutations remain 10 seconds. Neither the worker/provider/FFmpeg algorithms nor any SQL safety guard changed. Approved clips, immutable merged bytes, historical results, prices and authorizations are preserved.
