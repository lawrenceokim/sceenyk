### Support provider outcomes

These implemented rules preserve the existing provider/accounting boundaries. Status is trusted only after a Sandbox provider GET matches the stored instruction; webhook/redirect text and an operator's assertion are not sufficient.

| Verified provider evidence | Support reconciliation result |
| --- | --- |
| Item `SUCCESS`, local processing | Finalize the existing withdrawal Paid through the existing exactly-once accounting transition; do not debit Available again. |
| Item `SUCCESS`, already Paid | Financial no-op; record the support check without another payout/accounting effect. |
| Item `FAILED`, `DENIED`, `BLOCKED`, `CANCELED` or `RETURNED` before Paid | Apply existing definitive-failure rules to the processing withdrawal; restore only valid remaining reserved funds exactly once, retaining reversed amounts and original history. |
| Verified matching batch `DENIED` | Use the existing trusted batch-denial mapping; a mere missing item or failed lookup does not establish denial. |
| `PENDING`, `ONHOLD`, `UNCLAIMED`, `PROCESSING` or nonterminal batch status | Keep unresolved/processing with funds held; do not resend. Batch `SUCCESS` alone cannot mark Paid. |
| `RETURNED` or `REFUNDED` after Paid | Preserve Paid and append existing provider-return/review evidence once. No automatic credit, release, new deficit policy or resend; financial resolution remains outside version one. |
| Already Failed with the same failure evidence | Financial no-op; never restore twice. Conflicting terminal evidence, such as SUCCESS after a local failure/release, requires review without overriding the terminal record. |
| Unknown/unmapped status, GET error/timeout, missing persisted reference, or instruction mismatch | Preserve financial state, retain safe audit evidence and show an unresolved/review result. Do not infer Paid/Failed, release funds, edit IDs or send another payout. |

Missing-reference cases await existing verified webhook discovery or merchant investigation; the first support version has no manual reference-attachment control. An unresolved pre-Paid `REFUNDED` observation must not be treated as successful payment or automatic restoration without an approved existing mapping. Pending/eligible rows remain inspectable without invoking submission or changing their seven-day hold. Repeated/manual/automatic observations share the same terminal guards and accounting rules. Every support attempt, including no-op, failure and missing-reference results, gets an append-only audit outcome; audit attempts may repeat while money effects do not.

PayPal remains Sandbox-only. This unit performs existing-reference GET acceptance only; no new payout, refund, webhook/configuration change or finance override is authorized. Existing completion/delivery evidence below remains preserved.

### Sandbox payout implementation and required manual setup

The new adapter uses the current [Payouts v1 API](https://developer.paypal.com/api/payments.payouts-batch/v1): one USD EMAIL item per withdrawal at `POST /v1/payments/payouts`, stable server withdrawal UUID as both `sender_batch_id` and `sender_item_id`, then `GET /v1/payments/payouts/{id}`. The [official integration guide](https://developer.paypal.com/api/payouts) describes sender-batch deduplication and provider status reads. We conservatively never retry the POST, including on timeout; verified webhooks can discover a missing batch reference. Without a reference or webhook, processing remains held for manual merchant investigation.

Only matched item `SUCCESS` finalizes Paid; batch success/acceptance does not. `PENDING`, `UNCLAIMED`, `ONHOLD` and unknown states retain processing. Definitive item `FAILED`, `DENIED`, `BLOCKED`, `CANCELED`, `RETURNED` or verified batch denial release valid reservations once. Refunded/returned-after-paid observations append immutable provider-return evidence and show a support-review notice, retaining paid history and requiring support reconciliation; the implementation never silently reopens, re-credits or resends a paid withdrawal. Safe definitive API rejection names are retained as failure codes; raw provider bodies/credentials are never logged.

## Lifecycle and accounting

`credit_purchases` stores owner, Sandbox environment, pack snapshot, integer cents, currency, exact credits, persistent create/capture UUIDs, unique order/capture IDs and created/updated/completed timestamps. States: pending → approved → completed, plus failed/cancelled checkout outcomes. Only a verified completed final capture can grant credits. Cancellation cannot erase a raced verified payment; cancelled orders are not newly captured by reconciliation. Refunds, reversals, disputes and refund policy remain separate work.

Persist pending **before** PayPal creation to recover lost responses. Account-locked preparation reuses an outstanding same-pack purchase; a maximum of 20 new purchases/account/hour bounds new-record creation. Create uses the purchase UUID as `PayPal-Request-ID`; capture uses another persisted UUID. Unknown create retries are bounded to five minutes inside provider retention. An older unattached purchase remains pending for operator reconciliation rather than blindly creating another order. Authentic webhooks can recover an early/lost create response using the verified order's custom reference.

All browser mutations independently resolve Clerk → app user → owned purchase before PayPal HTTP. GET precedes capture to recover earlier successful POSTs. Only approved, uncancelled orders are newly captured. Timeouts/errors are uncertain; reread the same order and retain pending state. Browser success and elapsed time never establish payment.

Verification requires exact order identity, CAPTURE intent, one purchase unit, matching reference/custom/invoice IDs, expected amount/currency, completed order and exactly one final COMPLETED capture for the same amount/currency. `fulfil_paypal_purchase` then locks purchase and existing account, inserts an immutable purchase ledger entry, increments paid available credits and completes the purchase in one transaction. Unique purchase/order/capture/reference constraints arbitrate duplicates. Any failure rolls everything back; repeated completion returns the original outcome.

The existing ledger is extended, not replaced. Generation rows retain job linkage, movement constraints and unique job/type/reference rules. Purchase rows have no job and include purchase/order/capture IDs, type/reason `purchase`, positive available delta, zero reserved delta and `paypal:sandbox:<order>:<capture>` as unique reference. ## Webhooks and recovery

The exact webhook path bypasses Clerk middleware and always requires official `/v1/notifications/verify-webhook-signature` postback on the fixed Sandbox API. All five signature headers and the configured webhook registration ID are required. The original raw JSON is embedded unchanged. Certificate URLs must identify Sandbox notification certificates; Sceenyk never downloads arbitrary certificates. Request bodies are bounded to 256 KiB.

Only `SUCCESS` verification permits handling. Events trigger authoritative order rereads and the same capture/fulfilment path; payload amounts never mint credits. Provider/DB failures or unfinished approved captures return 503 for redelivery. Duplicate completed events return 200 after the idempotent outcome; invalid signatures return 400. Immutable order/capture effects deduplicate events without a separate event ledger. Official postback verification does not support mock simulator events; they are not real acceptance.

Page load, checkout return, browser activation and Check purchases reconcile at most five owned outstanding orders. This recovers refreshes, closed browsers and missed callbacks; registered authentic webhooks recover payments without the browser. There is no new cron/worker. Actual registration/delivery must be verified before claiming browser-independent recovery.
