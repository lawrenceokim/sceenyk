# Projects-page looping previews

Implemented in source on 2026-11-11. Deployment, remote migration and visual acceptance remain manual.

Only `/projects` cards use the new preview component. Card geometry, typography, links and actions are unchanged. Templates, Purchases, Marketplace and Studio do not consume this feature.

## Instant return navigation and private session memory (2026-11-11)

Projects now combines the installed Next.js 16 Activity behavior with a bounded browser-memory cache. It retains up to eight gallery pages, their card metadata and practical scroll positions, plus up to 48 media entries / 48MiB. Recently loaded cards render immediately on return, including through the Projects branch of the existing account loading boundary. The existing authenticated layout and server-derived ownership checks remain; no private data enters shared server caches, localStorage, IndexedDB, Cache API or service workers. There is no new dependency or application-wide caching flag. Initial visits and full browser reloads still load normally.

`ProjectsGalleryClient` owns one deduplicated request per page. A compact owned index reads project summaries and batched asset/generation/final/V3 revision fields; unchanged cards skip their full status, workspace and asset enrichment. Only changed cards are merged, keeping stable summaries and all unaffected media. Returning starts one background index check; overlapping focus/visibility checks share work and use a 15-second freshness window. Active generation checks run every 15 seconds; settled galleries run every 60 seconds, only while Projects is active and the document is visible. Local rename/delete results patch cached cards immediately and trigger a deduplicated check to reconcile ordering/pagination. Creation, Studio saves, worker progress/approval and changes elsewhere are discovered by the next active/return check without modifying those workflows or pages. A failed check retains cards and shows a small saved-content notice.

Completed preview MP4s and ordinary source-image thumbnails are delivered through owner-authenticated same-origin POST routes using private/no-store responses, then held as revocable Blob URLs in this session cache. This prevents a media download each time an offscreen player mounts again and avoids reliance on R2 browser CORS. Thumbnail images use a small 480px WebP derivative; the original source remains untouched. Source-video thumbnails, images larger than 20MiB and image conversion fallbacks retain the original signed-source rendering and browser-managed metadata/decoded-image reuse. Those fallbacks can download again after a route/element is evicted. Saved FFmpeg previews remain version-deduplicated in private storage.

Every cached media entry has at most five minutes of display authorization. Visible videos renew shortly before expiry to preserve continuous playback. After expiry media is hidden until the same server ownership/project-deletion/approval/version boundary authorizes it again. If the exact bytes are unchanged, the server renews authorization without transferring them again. Changed versions replace and revoke the old Blob URL; unavailable/deleted/rejected media retains the static fallback. A persistent Clerk resource listener clears snapshots, scroll state, pending downloads and Blob URLs on user/session changes or sign-out, including while Projects is inactive. Responses from a previous account or an invalidated media revision cannot repopulate the cache. An already-started bounded download may finish into memory after scrolling away, but only visible cards start media work or preview polling. Offscreen/hidden/reduced-motion players stop as before.

The new index uses existing verified tables/columns and requires no additional migration. Migration 112 and the media worker below remain necessary for FFmpeg preview creation. Large compact history projections are paged instead of accepting the default Data API row cap as a complete revision. Optional status/template-read failures on an initial load retain the existing unavailable-status/Publish fallback; failed background checks retain the previously loaded cards.

Focused verification: `node scripts/check-projects-session-cache.mjs` covers deduplication, unchanged snapshots, owner isolation, expiry/byte reuse, deletion, stale account responses, compact server projection, and private renewal without retransferring bytes. Manual acceptance remains with the owner: leave/return through links and Back, visit more than three routes, check pagination and scroll, rename/delete/create/save, generation/approval updates, hidden/reduced-motion behavior, sign-out/account switching, offline background checks, and expiry. No automated browser, full build, remote schema/provider/payment request or deployment is part of this change.

The client retains the existing thumbnail and requests a preview only when an approved card intersects the viewport, the document is visible and reduced motion is off. The silent video autoplays inline with no controls and loops its 3-second file. Loading, playback refusal and errors reveal the thumbnail. Leaving the viewport, hiding the tab or enabling reduced motion pauses and unloads the video and cancels polling. Browsers without IntersectionObserver retain thumbnails. The first request queues missing work; visible cards poll with increasing delay capped at 30 seconds until work completes. Leaving and returning retries the lookup without creating another job. Signed delivery is refreshed before expiry while visible.

`lib/projects/approved-video.ts` resolves owner-scoped live projects and stored current final approvals: V3 single-segment approved completed runs, approved nonrejected joined finals, and legacy final executions using the existing current-input RPC. Individual approved source clips do not qualify. It validates private source prefixes and binds a version hash to the saved output identity, storage key, ETag and SHA-256. Unavailable or incomplete evidence retains the thumbnail and grants no generation authority.

Migration 112 creates the explicitly new `project_video_previews` derivative queue/cache. Its only existing table dependency is `projects(id, owner_user_id, deleted_at)`, checked before installation; the composite ownership key already exists in the schema. Unique owner/project/version rows, service-only RPCs, RLS without browser policies, exclusive claims and fenced leases prevent duplicate processing across visits, tabs and worker processes. Successful previews are never requeued. Failed work has at most three attempts, with one-minute backoff. Expired claims recover after ten minutes; terminal failures retain thumbnails. Generation, approval, wallet, usage and payment tables are not modified.

The existing `scripts/media-preparation-worker.ts` processes one derivative at a time alongside its existing work. It rechecks ownership/version, reads and hashes the private final file, runs the existing bounded FFmpeg command wrapper, validates the output and conditionally publishes an immutable private MP4. Output is limited to 3 seconds, H.264, 15fps, 480px maximum dimension and 2MiB, with audio/subtitles/data/metadata removed. Restart or lost upload acknowledgement first checks the deterministic saved output key. Temporary copies are deleted; original files and approvals are untouched. The saved key is `users/{owner}/projects/{project}/project-previews/{version}.mp4`. The web route revalidates owner/approval/version before signing this exact key; responses and media use private/no-store delivery. No AI provider is invoked.

## Required setup

1. Apply `supabase/migrations/20261111011200_project_video_previews.sql` manually after migration 111, then deploy matching app and worker source. It is transactional and rerunnable. The migration was checked only against disposable local PostgreSQL fixtures; no remote schema installation is claimed.
2. Run/restart the existing FFmpeg worker with `npm run worker:media`. Its existing database service credentials, private R2 configuration and media-worker secret remain required. Production also requires the existing `FFMPEG_PATH` and `FFPROBE_PATH`. No new environment variables, public buckets, providers or payment setup are introduced. This does not require enabling paid video workers or Inngest.
3. Existing completed projects are queued lazily when their cards become visible. There is no bulk backfill or eager encoding during deployment. The first view keeps the thumbnail until the worker finishes. If setup or the worker is unavailable, cards retain thumbnails.

## Focused verification and manual acceptance

Run `node --conditions=react-server --import=tsx scripts/check-project-video-previews.ts` for the offline approval/queue security and synthetic FFmpeg checks. No hosted storage, real project/media, AI provider or payment requests are made by that check.

Manually inspect desktop/mobile in both themes: existing sizes/navigation/actions; silent looping only for approved final outputs; draft/incomplete/unapproved thumbnails; thumbnail during loading and playback/network failure; no preview requests before entering the viewport; pause/unload after scrolling away or switching tabs; reduced-motion changes; reusing the same stored preview after refresh or across tabs; different approved final versions receiving separate derivatives; and denied access for another account or a deleted project. Check the worker is running for first-preview creation. Browser autoplay refusal intentionally retains the thumbnail. Visual/hosted acceptance, deployment and remote setup have not been run here.
