## Canonical internal contract

Use one versioned internal **`VideoGenerationPackage`** contract with strict runtime validation shared by building, persistence, review and future adapters. The names below specify the intended contract, not installed TypeScript types, SQL tables/columns or an API endpoint. Refine exact persistence layout only in a separately authorized implementation after verifying the actual catalog.

| Concern / proposed field | Required content |
| --- | --- |
| `schemaVersion`, `compilerVersion`, `promptVersion`, `fingerprintVersion` | Interpret the contract, deterministic builder, neutral prompt compiler and canonical hash recipe. Preserve older readers or fail with an explicit unsupported-version state. |
| `packageId`, `packageVersion`, `supersedesPackageId` | Stable package identity, monotonic owner/project-scoped revision and optional prior version. Separate content version from a mutable command/lease concurrency version. |
| `project` | Trusted owner, project and originating UGC job IDs; saved input revision; title, creative direction, Creation Type UGC, video/UGC type, visual style and tone; provenance for all content-affecting settings. Never accept a client-authored owner or asset map. |
| `approvedInputs` | Exact approved Character reference/sheet and selected constituent view descriptors; Product / Prop reference/sheet/views; accepted Location image and relevant plan revision; approved Storyboard revision, command/content version, schema version and document digest. Include original-source provenance where needed without substituting originals for generated approvals. |
| Asset descriptors | Stable role/logical binding, immutable asset/candidate/sheet ID, source/workflow/review revision and approval version/receipt, approved timestamp, MIME, dimensions, byte length and cryptographic content checksum. Resolve existing ETag/object-version metadata privately for integrity checks. Never use an expiring URL as identity. |
| `storyboard` / `continuity` | Immutable approved structured document or its complete canonical scene/voice/continuity snapshot with document digest and exact origin. Identity, wardrobe, Product appearance and Location continuity carry across scenes. |
| `timeline` | Integer milliseconds, total duration and ordered stable scene identities. Start at 0, end exactly at selected duration, with continuous non-overlapping scenes and explicit transition instructions. Current UGC durations are 5/10/30 seconds. |
| `scenes[]` | One package per approved scene: number/ID and source scene binding, exact absolute `startMs`, `endMs`, derived duration, purpose/description, timed actions/gestures/facial reactions, Product interaction/position, Character/Product/Location bindings, dialogue/narration, camera, lighting, audio intent, transition, continuity and additional approved directions. Preserve scene order. |
| Scene camera/light/style | Shot, angle, framing, movement, zoom/focus; lighting direction/intensity/colors/atmosphere; effective visual style, tone and video type. Inherit only explicit validated package defaults. |
| `voice` and scene speech | One approved Character voice description/pace and stable logical voice binding; narration enablement and approved instructions; exact utterance text, speaker role, Character binding, delivery and absolute start/end ms. | `generationPrompt` per scene | Provider-neutral prompt deterministically compiled from the same approved structured fields and bindings, with compiler/prompt version. No new creative content or endpoint parameter names. Structured fields remain authoritative; preserve source prompt provenance and reject contradictions. |
| `output` | Selected aspect ratio, exact duration and required video/audio behavior; provider-neutral resolution/dimensions, frame rate and format requirements where explicitly decided. | `requirements` | Derived feature requirements, including reference roles/counts, multiple scenes, audio/dialogue/lip-sync when actually required, exact timing, ratio, resolution and seed policy. The package references **exact approved versions**, not “latest” lookups. Require exactly one approved Character, one Product / Prop and one Location for current UGC V1. Reference counts for individual approved views/sheets are explicit; do not assume three semantic roles mean three provider images. Every scene resolves bindings into this frozen manifest under the same owner/project. No new person, product, environment, claim, narration or unsupported capability may be inferred during packaging.

The internal payload and server-only asset resolver may retain private storage descriptors. Owner-facing summaries use a separate safe projection, not the full privileged package. No credentials, raw provider payloads, private R2 keys, signed URLs or full worker records enter browser/public/template DTOs or logs. Publishing/adoption continues through the separate public-safe logical-slot projection in [UGC V1](ugc-v1-workflow.md#ugc-template--marketplace-contract).

## Fingerprinting, immutable versions and staleness

Define and version a canonical serialization recipe: strict validated JSON, recursively sorted object keys, preserved scene/action/speech/reference array order, exact approved strings, integer-ms/numeric representations, explicit optional/null handling and UTF-8 bytes without formatting whitespace. Reject non-finite/ambiguous values; do not use incidental database JSON formatting or strip meaningful dialogue whitespace. Compute SHA-256 over a domain/version-prefixed canonical representation.

- **Input fingerprint:** include owner/project scope, exact source input/content revisions, all approved asset IDs/content checksums/source and approval versions, approved Storyboard revision/version/document digest, relevant saved settings (names/direction, video type, style, tone, aspect ratio, duration, narration/voice/output requirements), and builder/schema/prompt/fingerprint versions. It identifies equivalent preparation inputs within the authorized project, never across owners.
- **Package integrity hash:** cover the immutable canonical content, including compiled scene prompts and technical requirements, using a fixed recipe that excludes the hash field itself. Exclude generated package IDs/revision numbers, creation/approval timestamps, transient URLs, state, attempts/leases, future provider selection/payload/job IDs and quote/billing metadata. Input provenance approval receipts remain bound through the input fingerprint. Generated envelope values must not defeat deduplication.
- **Separate identities:** input fingerprint prevents duplicate builds; package hash proves content integrity; the explicit client build-request key identifies a command; a future paid-execution key identifies an admitted provider operation. None grants ownership, approval or permission to charge, and a hash does not promise deterministic AI output.

If Character, Product, Location or Storyboard is edited, replaced, regenerated, rejected/deleted, loses approval, or has a different approved version/content proof, mark the package **stale**. Changes to important saved project settings, dialogue/voice, output intent or compilation contracts also require rebuilding. Keep the prior content and approval audit unchanged, but make it ineligible; reverting visible values cannot revive an obsolete approval/version silently. Non-content UI preferences and worker heartbeats do not change the fingerprint.

Compare current dependencies at build admission, final persistence, read/status projection, explicit package approval and future execution admission. Use database transaction/locks and expected revision/version checks at mutations so concurrent saves cannot approve or commit a package against newer inputs. Event-driven invalidation is an optimization; authoritative checks must still catch missed events. Missing/hash-mismatched private media blocks validation/execution even if the original fingerprint was correct. A race discovered before commit stores no reviewable valid package; record the failed/stale build attempt separately.

Rebuilding creates a new immutable package version from current approved inputs and requires new explicit approval. It never overwrites approved content, repairs upstream assets, regenerates Storyboard, silently adapts required settings or reuses old financial confirmation. Prior versions remain private audit history under the eventual retention policy.

## Provider interface and configuration

Define a generic **`VideoGenerationProvider`** boundary. The following operations are a planned interface responsibility list, not implemented methods or authorization to execute them:

| Responsibility | Contract |
| --- | --- |
| Provider identity/configuration | Resolve an explicit server-owned target and versioned model/capability/settings configuration. Provider endpoint/model IDs and credentials belong exclusively to adapter/configuration code. Core logic consumes neutral capabilities and safe configuration identity only. |
| `getCapabilities` | Return locally configured, versioned declared capabilities for the selected model/mode/account. No network discovery or paid request during M9. Unknown/unverified capability is distinct from supported. |
| `validatePackage` | Pure preflight: compare neutral package requirements against the declared capabilities; return supported, unsupported or unverified with safe field/scene-specific reasons. Do not rewrite the package. |
| `translatePackage` | Deterministically map the approved canonical package into that provider's payload and per-scene execution manifest. Raw payloads/types stay inside the adapter. Resolve ephemeral owned-media access only at future execution, outside persisted canonical content. |
| Future M10 execution | Submit an admitted operation with a durable idempotency context; recover/poll the same provider job and normalize statuses/results/errors. Optional cancellation/webhook support is advertised explicitly. No network method is reachable from the M9 builder, approval, retry or recovery path. |

fal.ai will be the first implementation of this interface in a separately authorized unit. Each future adapter translates the **same** package contract. SDK imports, field names, model IDs, supported modes, request limits, seeds, price/cost assumptions and provider settings remain inside provider configuration/adapters. Do not spread `fal` branches through Storyboard, package building, project logic, persistence or UI. Existing legacy fal code can be evaluated for narrow reuse later; it is not proof that its hardwired scene API satisfies this interface.

Provider selection and resolved adapter/model/configuration/capability versions are frozen in a separate future execution record bound to package ID/version/hash, not baked into canonical creative content. An explicit provider/configuration change requires fresh capability checks and invalidates any prior execution quote/confirmation. A still-current canonical package can be reused when its required content/settings do not change; any creative/timing/reference adaptation requires a new package version and approval. **No silent provider or model fallback.**

## Capability checks and paid-request safety

Actual provider limits remain **Needs confirmation** against the selected model/API version and account before implementation/execution. No capability values or costs are asserted by this plan.

| Capability | Fail-safe check |
| --- | --- |
| Image/reference support | Check conditioning modes, sheet/individual-view inputs, required Character/Product/Location roles, formats/dimensions/size and maximum reference-image count for the actual request. Never drop a role/view silently to fit a limit. |
| Audio/dialogue | Distinguish silent video, native audio, speech, dialogue/narration, lip-sync and externally supplied audio. Preserve exact utterance/voice intent. Unsupported required audio blocks execution; no automatic TTS/provider substitution. |
| Duration | Validate each scene and total duration against per-request min/max/discrete increments and output timing guarantees. A 5s/30s package is not automatically compatible with another API's scene lengths. No silent padding, trimming, time stretching or dialogue speedup. |
| Aspect ratios | Match the explicit ratio and orientation to the mode/model; no automatic crop or ratio substitution. |
| Resolution/output | Validate required dimensions/resolution, frame rate, format and audio output, including cross-constraints with duration and mode. Unknown requirements/configuration remain a blocking preflight result. |
| Scene generation | Check per-scene versus multi-scene support, continuity/reference requirements and exact approved boundaries. Provider segmentation must preserve timing/bindings; unsupported assembly or boundary fidelity cannot be assumed. |
| Seed | Check seed type/range and determinism semantics when required; optional seed absence is allowed only by the package's declared policy. Never promise reproducibility merely because a seed exists. |
| Asynchronous jobs | Advertise sync/async behavior, durable remote job identity, polling/retrieval, timeout/cancellation/webhook and idempotency/recovery support. If the execution mode cannot meet required durable recovery, block submission until an explicitly reviewed strategy exists. |

M9 validates canonical completeness and may display an offline compatibility assessment from reviewed configuration. **Canonical validity/package approval and provider readiness are separate facts.** A valid neutral package may be reviewed while provider readiness is unverified; its summary must say execution is blocked. Unsupported required features or unknown capability/configuration block any future paid call. Package approval is never cost consent.

Immediately before any later paid submission, revalidate ownership, current approvals/fingerprint/hash, package approval, selected capabilities/configuration, exact mapped payload and trusted asset access, plus existing current quote/explicit confirmation and server-enforced financial admission. Persist submission intent/idempotency identity **before** the call. If any required feature cannot be represented, stop before charging/submitting and show the specific reason. Any separately proposed adaptation needs owner review, rebuilding/reapproval when content changes, and a new matched quote where applicable.

## Workflow and failure states

**Approved Storyboard → Build Generation Package → Validate Package → Persist immutable package/version → Display package summary/status → Approve package → Pause before video provider execution.**

1. The owner explicitly requests a build from the current approved Storyboard and all current upstream approvals. The server resolves trusted saved inputs and records one idempotent build request; it does not generate or approve upstream content.
2. The existing local worker, when later implemented and manually started, compiles a deterministic candidate from frozen approved data, runs schema/business/timing/binding/integrity checks, and compares the current dependency manifest again at commit. No OpenAI, image, voice or video request is part of packaging.
3. Commit the validated immutable payload/hash/dependency manifest and successful validation receipt atomically with the review transition. Persist invalid build diagnostics separately; incomplete output must never appear as ready for approval.
4. Display a private owner summary: package version, Storyboard/asset approval provenance, scene count/timing, settings/voice/output intent, validation result, freshness, compatibility status and safe failure/rebuild guidance. Show real persisted progress and reload it on reopen. No fake output or video preview.
5. Explicit Approve uses package identity plus expected command version/hash and current-input checks. Append an approval receipt binding owner, package version/hash and time. Repeated approval returns the same outcome; stale tabs or changed content fail safely.
6. Persist approved-and-paused status. Do not dispatch a provider, enter video generation/finalization, reserve/consume credits or mark the UGC run Complete. M10 remains Not Started. Later video execution still needs its own explicit authorization, capability checks and existing financial gates.

Planned build lifecycle labels: queued, building, validating, saving, review, approved-and-paused, failed and cancelled. Track stale/blocked eligibility separately so immutable content and historical approval remain intact. These are specification labels, **not new database enums**. Failure reasons distinguish missing approval/asset, invalid timing/binding/schema, stale inputs/version conflict, persistence failure, unsupported capability, unverified configuration and interrupted/reconciliation-required work. Capability blocking must not masquerade as a corrupt canonical package or trigger fallback.

## Persistence, idempotency and restart recovery

- **Scope and authority:** every build/read/approve/rebuild/retry independently verifies authenticated application owner → project → UGC job → exact source/package relationships. Background workers reload trusted relationships. Database fencing/RLS/grants remain authoritative; client controls alone are insufficient. Idempotency collisions across users/projects cannot disclose or reuse content.
- **Duplicate prevention:** bind the build-request key to owner/project and input fingerprint; same key/same content returns the existing attempt/package, same key/different content conflicts. Atomic uniqueness/locking on compatible scoped input fingerprint plus compiler version prevents two distinct clicks from building duplicate current packages. Changed inputs/compiler produce a deliberate new version; do not bypass a failed/uncertain operation by inventing another key.
- **Immutable snapshots:** store canonical structured JSON, provenance, digests and validation receipts in private PostgreSQL metadata. Preserve exact source versions and enough frozen document data to interpret them later without resolving “latest.” Reuse private R2 media; store stable descriptors, never binaries/base64 or signed URLs in the package. No new bucket/table/column/migration is assumed or added here.
- **Durable work:** extend the existing local job/lease/checkpoint model rather than introducing Inngest, Render, another queue or a long web request. Use atomic claims, lease tokens, heartbeats, optimistic command versions, bounded retries/backoff and append-only safe events. Preserve upstream completed work; a stale worker cannot commit after losing its lease or after input changes.
- **Restart recovery:** reload the same frozen build request, checkpoint and input fingerprint. Reuse a committed matching package after a lost acknowledgement; otherwise deterministically recompile the same candidate and conditionally commit once. Recheck freshness; stale work requires an explicit rebuild. A crash before commit cannot create an approved partial package. Persistence failures leave clear retryable state and never trigger provider work.
- **Future remote uncertainty:** M10 must persist the selected adapter/configuration, scene operation identity and submission intent, then remote job ID/receipt/result. Recover the same operation after restart. Provider idempotency is used only if documented; local deduplication does not guarantee exactly-once remote billing. Unknown submission outcome stops for reconciliation, never automatic repurchase or fallback.
- **Deletion/retention:** package history does not authorize deletion of approved/upstream media or changes to existing rejection behavior. Coordinate future retention with exact referenced versions. If a dependency is deleted/unavailable, preserve the package's audit metadata but block eligibility; never retarget its asset pointer. Reference pinning/retention and erasure policy need confirmation before dependent implementation.
